# Птичий двор — инструкция серверному агенту QuRa

Дата: 02.11.2026. Это подготовленный клиент и контракт интеграции, **не включённая экономика**. Публичный прототип использует тестовые GE и локальный прогресс. Не переносить их в кошелёк, инвентарь или рейтинг пользователя.

## 1. Входная точка и границы работы

Рабочий репозиторий: `gselfman/poultry_yard`. Целевое приложение: `gselfman/QuRa`, `/opt/QuRa`, FastAPI + PostgreSQL + Next.js. Сначала заново прочитать актуальные `AGENTS.md`, `CLAUDE.md`, `docs/AGENT_LOOP.md`, `docs/ENVIRONMENT.md`, `docs/NEIGHBOR_SERVICES.md`. Эта инструкция не отменяет правила хоста и ревью.

В QuRa работать в отдельной ветке и PR, с ревью текущего HEAD и зелёными проверками; деплой только из принятой чистой `main`. Финансовые изменения, auth и миграции проходят предусмотренное QuRa согласование. Не менять `/opt/vdar`, соседние сервисы и их порты. Повседневные операции — через `qura-ctl`; не собирать Next на живом процессе и не занимать порт радио 8100.

Проверенные исходные точки интеграции (на дату инструкции; перечитать перед реализацией):

| Файл QuRa | Что переиспользовать |
| --- | --- |
| `app/api/routes/volk.py` | `CurrentAuth`, `DbSession`, feature gate, строгие Pydantic-модели, rate limit |
| `app/services/volk.py` | блокировки игрока/сессии, идемпотентные операции GE, replay, batch sequence/digest, settlement |

Сервис лутбоксов и действующий каталог в этой работе не были достоверно найдены. Найти их на сервере/в текущей ветке QuRa, не создавать параллельный инвентарь. Если их ещё нет — отдельный согласованный PR с хранением entitlement/open/result и каталогом.

## 2. Что уже есть в коде

- `radio.js`: прямой поток QuRa, включение нажатием, отдельная громкость, выключение закрывает поток; ограниченный reconnect с backoff.
- `runtime-policy.js`: публичный прототип не загружает пульт и старые локальные настройки. Интегрированная сборка закрыта, пока не подключён авторитетный host adapter (`INTEGRATED_HOST_READY=false`). Нельзя просто сменить этот флаг и выдать локальные результаты за проверенные.
- `integration-client.js`: транспорт для bootstrap/session/batch/quote/purchase/settle и двухэтапной публикации баланса; CSRF, same-origin credentials, idempotency key, защита одновременного повторного запроса.
- `session-replay.js`: общий seeded RNG и шаг 1/60, команды движения/карточек/эволюций/продолжения/покупок. Строительный блок будущего replay, **пока не подключён к `game.js` и HTTP-сервису**. Проверена повторяемость в Node на коротком сценарии; кроссбраузерные десятиминутные replay ещё не аттестованы.
- `balance-config.js`: список числовых настроек, диапазоны публикации, запрет валютных цен и тестовых флагов. `lab.js`: только авторизованный sandbox, подтверждение публикации, If-Match revision.
- `reward-milestones.js`: два отдельных достижения из состояния симуляции; сам ничего не начисляет.
- `integration/reward-policy.json`: отключённая заготовка бизнес-политики, не серверная конфигурация.
- `collision-index.js`: пространственная выборка для обычных снарядов, точная геометрия и исходный порядок попаданий сохранены. Взрывные снаряды проверяются полным проходом, поскольку могут оттолкнуть следующие цели.

## 3. Сессии и доверие к результату

Подключить браузер к тому же fixed-tick driver, что исполняется в изолированном серверном worker. Сейчас `game.js` вызывает `step()` с кадровым dt и локальными действиями; это **нужно заменить в интеграционном PR**. Не начислять ничего по клиентским `bossEvents`, `kills`, `score`, `xp`, `chest` или localStorage.

Старт: авторизовать пользователя; проверить блокировку/feature flag/владение героем; заблокировать player/progress; вернуть существующий старт при повторном key; списать один билет и создать сессию атомарно. Seed создаёт сервер, конфигурация и версия движка фиксируются на сессию. На аккаунт одна активная сессия; политика TTL/resume и компенсации технически не начатого забега должны быть явными и идемпотентными. Сбой до commit не расходует билет.

Каждая сессия хранит: user_id, session_id, status, seed, protocol/engine hash, balance_revision, immutable balance snapshot, reward_policy_version, ticket debit id, last_seq, processed_tick, replay checkpoint, milestones, paid_rerolls, revive_used, timestamps, terminal receipt. Не доверять переданному user_id/email. Sandbox помечать **на сервере при создании**, без билетов, GE, XP, лута, рейтинга и открытия героев.

Batches: строгая схема, ограничение размера/числа команд, конечные числа и диапазоны; возрастающие tick и seq. Повтор seq с тем же digest возвращает прежний ответ, с другим — 409. Проверять реальное серверное прошедшее время (невозможно прислать 10 минут за секунду), лимит паузы/активного времени, допустимость выбора и владение сессией. Не запускать Node через shell с пользовательским JSON; пул изолированных workers, timeout, лимиты CPU/памяти/очереди. Нагрузка replay на сервер и поведение после рестарта требуют отдельных замеров.

Нельзя смешивать версии JS во время забега. Сохранять старые версии движка и конфигурации до окончания их сессий. Различия floating point / `Math.sin` между средами проверить golden-replay тестами; при расхождении не начислять автоматически, сохранять технический статус для расследования, не списывать повторно GE.

Сначала внедрить приём серверных состояний/receipt в UI, resume/reconnect и обработку offline. Завершение без связи должно показывать «Результат проверяется», повторять **тот же key**, а не рисовать успешную выдачу. Только после этого и acceptance-тестов менять `INTEGRATED_HOST_READY` в reviewed PR.

## 4. GE: только существующий ledger

Внутриигровые семечки и уровень — `run_xp`, не GE и не XP аккаунта. `createGame().ge=50`, `purchaseQuote()` и `openRunChest()` — прототипные механизмы; на проде они не являются источником денег/предметов. Начальный баланс берётся сервером из общего кошелька, а не из createGame/localStorage.

Правила: бесплатно каждые 5 уровней, бесплатные копятся только внутри забега и тратятся первыми. До 3 **платных** перебросов по 5 GE. Одно воскрешение за 20 GE строго до 600 секунд; после Индюка не возобновлять доступность. Не менять цену через баланс-пульт.

Для платного действия сервер выдаёт краткоживущую quote: quoteId, action, price, balance, balanceAfter, expiry, sessionId, stateRevision. UI показывает действие, цену и остаток, ждёт отдельного подтверждения, блокирует повторное нажатие и движение. Purchase под блокировками проверяет quote, свежий баланс/режим, лимиты, бесплатные перебросы и срок; списывает и сохраняет право на ровно одно действие в одной транзакции. Replay принимает платную команду только по сохранённому серверному receipt, а не по boolean/receipt из клиента. `authorizeSpend` в driver по умолчанию запрещает всё; callback заполняется только сервером.

После восстановления процесса хранить полную последовательность команд и seed либо реализовать полноценную сериализацию RNG/Map/Set/checkpoint; текущий driver не предоставляет durable checkpoint codec.

Ключи, например `poultry:{session_id}:purchase:{quote_id}`, с UNIQUE constraint. Повтор возвращает то же списание/receipt. При неопределённом сетевом исходе запрос статуса/повтор того же key. 402/409/410 требуют обновить quote, без автоматической повторной оплаты. Деньги — PostgreSQL ledger, сбалансированные проводки `post_transaction` по образцу `volk.movement`, не float и не новый кошелёк. Суммы/источник эмиссии и лимиты — серверная политика QuRa.

## 5. Билеты, ежедневные задания и XP аккаунта

Рекомендуемая схема: общий существующий запас билетов, **один билет на вход**; отдельный код игры `poultry_yard`. Это значение пока proposal в отключённом JSON, утвердить до включения. Автоматический GE fallback на вход выключен: пользователь его не заказывал. Если нужен платный вход — отдельная цена/quote/подтверждение, не переиспользовать бездумно `game_v1_volk_entry_ge`.

Текущий `entry_cost()` в QuRa заточен под Волка и может вернуть GE-цену при отсутствии билетов. Обобщить в совместимую функцию с game code или добавить poultry-обёртку с теми же блокировками; **не списывать одновременно билет и GE**. Не ломать существующий вход Волка. Окно начисления и timezone — как текущие билеты QuRa.

Добавить подтверждаемый триггер **`PLAY_POULTRY`**: «Сыграть в Птичий двор», «Завершить забег по билету». Он срабатывает на валидный won/lost terminal забег с ticket debit, не на start, перезагрузку, sandbox или abandoned. Для voluntary bonus терминальное событие выдаётся при завершении/гибели, а не дважды на Индюке и на финале. Раннюю осмысленную квалификацию/защиту от умышленной мгновенной смерти утвердить в серверной политике, не доверять клиентскому таймеру.

В текущей QuRa quest/ticket сервисы ещё проверяют `game_v1` и tester allowlist. Расширять rollout отдельно по её правилам, не удалять эти проверки глобально ради одной игры.

XP аккаунта начислять как у существующего задания Волка через `record_quest_trigger`: общий дневной cap, журнал событий, текущая основная курочка, серверная дата МСК. В текущей QuRa default daily quest = 12 XP, это **не 12 за каждый повторный запуск**. Не конвертировать десятки тысяч семечек 1:1 в аккаунтный XP. Если дополнительно нужен XP за каждый валидный забег — сначала утвердить сумму, общий дневной cap и отдельный идемпотентный тип события; сейчас такой тариф не задан и не включён.

`FREE_DAILY` сейчас содержит три задания, а завершение всех считает ровно 3. При добавлении Poultry явно решить: выбранные три из пула или четыре задания; синхронно менять selection, UI, all-complete threshold и тесты. Задание не должно принуждать покупать GE: при назначении обеспечить билет либо выбрать другое доступное задание. Выдача целевого билета за назначение — максимум один по UNIQUE(user,day,quest), только если такая политика утверждена; не бесконечные билеты через обновление страницы. Ошибка уведомления/задания не должна отменять уже зафиксированный игровой результат; использовать outbox/retry или согласованный savepoint, исключить потерю XP после технического сбоя.

## 6. Лутбоксы и курочки — два разных достижения

**За первую Цесарку в забеге — самый слабый лутбокс (`weak`), а не главный сундук.** Привязать к наименьшему тиру существующего каталога. Не выдавать за него 21–67 GE и гарантированный аксессуар главного сундука. Точное слабое содержимое/веса пока не определены: `catalogId=null`, выдача отключена до утверждения. Победа впервые на аккаунте также открывает Рэмбо, независимо от случайного приза.

**За Индюка — главный лутбокс (`main`)**: 21–67 GE и один случайный аксессуар из разрешённого каталога QuRa. Диапазон включительный. Победа впервые на аккаунте открывает Монаха. Никаких `prototype-*` аксессуаров на проде. Ряба открыта сразу. Повторное открытие курочки не создаёт дубликаты.

Достижение резервирует entitlement по UNIQUE(user_id, session_id, milestone); повторный boss event/replay не выдаёт второй. Сохранять подтверждённый milestone после replay checkpoint, чтобы аварийное закрытие браузера не уничтожало заслуженный сундук. Главный сундук открывается **на итогах**, после завершения забега или гибели в добровольной бонусной волне; победа не заставляет продолжать. Для weak использовать такой же экран результатов как единый понятный этап выдачи; при ином UX сохранить ту же серверную идемпотентность.

Призы выбирает серверный криптографический RNG, один раз, с сохранённой версией таблицы вероятностей и окончательным результатом. Open endpoint повторяет сохранённый результат; disconnect, новая вкладка или повтор settle не перевыбирают приз. В одной транзакции/надёжном outbox: пометка открытым, GE ledger, inventory grant и receipt. Не терять уже выданную часть и не начислять её повторно при retry. Общие дневные лимиты лута/GE, duplicate-accessory policy, компенсации и выдача после session TTL ещё требуют утверждения. Пока они не заданы, reward feature flag держать выключенным.

Один рейтинг для всех ranked игроков, без деления по герою/GE. Формула и tie-break ещё не утверждены — не публиковать клиентские очки как окончательный рейтинг. Sandbox исключить. В leaderboard показывать серверные результат/аватар, безопасно экранировать имена.

## 7. Мастер игры и стандартный баланс

Администратор в существующей админке вводит email; сервер находит **единственного существующего подтверждённого пользователя** и назначает ему отдельное право `poultry_game_master` по user_id. Не назначать по query string/localStorage/JS, не делать любого админа автоматически Мастером. Отзыв права действует немедленно для всех write endpoints, ведётся аудит кто/кому/когда назначил/отозвал. Email не включать в публичный bootstrap.

Обычный пользователь не получает пульт. Мастер открывает **sandbox**, сервер отдаёт authenticated=true, permissions.poultry_game_master=true, session.kind=sandbox, rewardsEnabled=false, csrfToken, balanceRevision. `masterSandbox()` проверяет эту форму только для UI; backend обязан проверять реальную роль из БД на каждом запросе, это не механизм авторизации сам по себе. Sandbox и ranked должны жить в изолированных вкладках/процессах либо с неизменяемыми snapshots конфигурации: engine exports сейчас mutable, нельзя подменить общий баланс активного ranked забега.

Редактирование — локальная тестовая сессия. Неуязвимость, heal/clear/spawn/time jump/автовыбор, текущие HP/оружие/пассивки никогда не входят в published snapshot. В `balance-config.js` задан числовой allowlist с диапазонами, ограничены HP/защита/количество врагов, заблокированы GE-цены. Портировать эти правила и cross-field checks на сервер; клиентскую валидацию нельзя считать защитой. Проверить minInterval≤interval, lateStart<lateEnd, transitionStart<transitionEnd, вероятности/плотность, ненулевой урон/поток, безопасные максимумы расходов CPU. Версионировать полный schema отдельно от настроек.

Публикация — **два отдельных серверных действия**:

1. prepare: повторно проверить роль+CSRF+If-Match, весь payload и ranges; посчитать diff от опубликованной версии; создать одноразовый confirmation token на 60–120 с, привязанный к user_id, revision и hash точного draft; вернуть diff. Пустое изменение не публикуется.
2. UI показывает «для всех новых забегов», diff и критичные изменения, затем отдельное подтверждение пользователя. publish получает только token, не новый values.
3. publish: заново проверить роль, CSRF, expiry, draft hash, limits и revision; атомарно consume token, записать immutable revision + audit + active pointer. Idempotency возвращает тот же результат, повтор token не создаёт новую ревизию; stale revision →409.

Текущие ranked забеги остаются на старом snapshot. Есть история и rollback через такую же подтверждаемую операцию. Перед выдачей всем — sandbox smoke/автотесты. Частичные/NaN/Infinity/неизвестные поля отвергать, произвольные пути не применять через unsafe object merge. Старый `poultry-lab-v5` из localStorage не загружается для обычных игроков и не становится глобальным дефолтом.

## 8. Контракт HTTP

`integration/poultry-api.openapi.json` — **новые проектируемые endpoints**, не утверждение, что они уже есть в QuRa. `/api/poultry` удобно проксировать Next к backend-router по паттерну `/gamezone/volk`. Все routes same-origin, аутентификация/CSRF по текущим QuRa conventions. POST: Idempotency-Key + canonical body hash; reuse key с другим body →409. Выдача чужой сессии/quote запрещена, cookie HttpOnly/Secure/SameSite, Origin allowlist, нет CORS `*` для credential API.

Bootstrap отдаёт фактические баланс/билеты/unlocks/permissions/activeSession/configRevision, не клиентские цифры. API ошибки: 401 auth, 403 blocked/role, 402 insufficient GE, 409 stale/sequence/key conflict, 410 expired quote/session, 422 invalid payload, 429 rate limit, 503 disabled/overload. Клиент ничего не выдаёт при ошибке.

Дополнить API inventory/lootbox routes по существующему QuRa сервису, не изобретать альтернативный денежный контракт. Секреты только сервер, в JS нет admin email whitelist, токенов ledger или ключей подписи.

## 9. Сборка и безопасный выкат

Node 22+; npm install для standalone-клиента не нужен. Из root репозитория:

```bash
node --test tests/*.test.mjs
node tests/bench-crowd.mjs
node build-runtime.mjs
node build-runtime.mjs --production
```

В Site layout те же тесты находятся в `dist/tests`. Скрипт сам выбирает root/dist. Обычная сборка → `build/` (публичный тестовый прототип); production candidate → `build-production/` (fail-closed до host integration). `release-manifest.json` содержит SHA-256 файлов и `financialIntegrationReady:false`. Это сознательный блокер: сначала подключить adapter и заменить манифестный флаг после испытаний в том же reviewed PR. Не публиковать `dist`/корень целиком: там tests, бенчмарки и архивные ассеты. `perf.html` и старый renderer не попадают в сборки.

В QuRa поместить статику в версионированный каталог, например `/games/poultry/<release>/`, исправив относительные asset URLs/route proxy, либо перенести компоненты в текущий Next route. Документация не задаёт существующий route как факт. Manifest/index/runtime-mode no-cache; версионированные assets immutable; atomically переключать ссылку релиза, хранить предыдущий для rollback и активных сессий. MIME js/css/webp/font, gzip/brotli, HTTPS. CSP учитывает `media-src 'self' https://qura.one` (и фактический redirect origin радио, если появится), script/style policies адаптировать к нынешним inline styles; не ослаблять auth CSP всего приложения без ревью.

Радио уже играет из `radio.js`, звуки боя независимы. Не копировать большой MP3 в репозиторий. Проверить живой stream MIME/байты по `docs/RADIO.md`, autoplay gesture на iOS/Android, выключение прекращает загрузку, volume на iOS может управляться только системной громкостью. Cross-origin прототип проверен в Chrome; мобильные и фоновое аудио ещё нужно проверить. Никакого отдельного Icecast/порта/ffmpeg для игры не создавать.

Миграции: уникальный следующий номер и одна ожидаемая Alembic head, backup/план rollback, уникальности/индексы для session start, batch seq, quote consumption, milestone, settlement, inventory grants, config revision/audit. Отключённые feature flags → миграции → staging → staff → ограниченный rollout → все. Kill switch останавливает новые старты/награды без потери уже подтверждённых операций; очереди retry сохраняются. Клиентский флаг не управляет финансовым feature gate.

## 10. Обязательная приёмка до реальных наград

- Два одновременных старта расходуют максимум один билет; retry не расходует новый. Волк продолжает работать.
- Повтор/reordered/forged batch, ускоренные tick, другой engine/config, чужая сессия и поддельная победа не дают XP/GE/лут.
- Free rerolls first; ровно 3 paid; revive один до 10:00; каждая трата подтверждается; две вкладки и retry не удваивают расход.
- Цесарка → weak, Индюк → main; оба once per run; hero unlock once per account; re-open возвращает тот же prize; смерть/добровольный бонус/TTL/рестарт не теряют entitlement.
- PLAY_POULTRY только валидный ticket terminal; XP once/day по заданию и общий cap, никакого переноса run_xp; повтор settlement/outbox не дублирует.
- Не-Мастер получает 403 на все admin routes независимо от JS. Revoke до publish, expired token, changed draft, stale If-Match, double submit, unsafe HP/god/валютные цены отклоняются. Старые ranked snapshots не меняются.
- Replay Node↔Chrome↔Safari: полные 10 минут, все оружия/покупки/паузы/боссы, hash и итог совпадают; в driver сейчас нет UI pause/resume integration, добавить их в host protocol до выпуска.
- Реальные Android/iPhone: safe areas, плавающий joystick без кликов по UI, скролл карточек, возврат из background, resize; радио on/off/volume; нет мерцания/обрезанных предупреждений.
- Профиль 5/10/15 минут, плотная волна, 600 врагов, тысячи семечек и разные оружия. Собирать frame p50/p95/p99, long frames >50 мс, heap/GC, память картинок, dropped frames; не писать в логи содержимое кошелька/email/токены.
- Сервер replay CPU/очередь, PostgreSQL locks, радио throughput, restart/resume и canary rollback. Мониторинг повторных выдач/небалансных проводок и ошибок каталога.

До прохождения этих пунктов статус — staging/integration candidate; запуск с реальной экономикой запрещён feature gate. Отчёт серверного агента должен назвать commit, миграции, CI/review, тестовые receipts и фактически проверенные устройства, а не просто «всё готово».
