## Проверки

Автоматические проверки: **137/137 пройдены** (`node --test tests/*.test.mjs`, в Site — `dist/tests`). В том числе выборка столкновений на случайных сегментах, обновление после отталкивания, отсутствие публичного пульта, запрет небезопасных параметров/цен, CSRF и double-submit transport, радио/retry/stop race, повторяемость seeded simulation, сохранение семечек и урона. Дополнительно сравнены состояния нового и прежнего движка: четыре сочетания эволюций, по 600 шагов с 300 врагами; итог и промежуточные снимки совпали. Обе сборки подготовлены; production-режим не разрешает запуск локальной экономики.

Node benchmark, один и тот же seeded сценарий, 600 врагов + 500 снарядов + 10 000 семечек, 60 прогревочных + 180 измеряемых шагов, сервер этой сессии:

| Расчёт одного шага | До | После |
| --- | ---: | ---: |
| Среднее | 31,52 мс | 9,15 мс |
| p95 | 58,52 мс | 14,35 мс |
| Максимум в выборке | 97,13 мс | 20,30 мс |

Среднее улучшилось примерно на **71%**. Это синтетическая CPU-проверка, **не обещание 60 FPS на телефоне**. Сценарий содержит много неподвижных снарядов и распределённый опыт; разные реальные сборки/плотная ближняя толпа могут иметь другую стоимость. Повтор: `node tests/bench-crowd.mjs`. Максимум и heap зависят от JIT/GC/соседней нагрузки; отдельный достоверный профиль сборки мусора и мобильного GPU ещё нужен.

В браузере проверены меню, скрытый пульт, радио и начало забега. В отдельной тяжёлой браузерной сцене (506 видимых из 600 врагов, 500 снарядов, 9 999 семечек, 239 измеряемых кадров) работа JS/canvas дала p50 33,6 мс, p95 101,3 мс, max 1 495,1 мс. Интервал requestAnimationFrame был около 1 016 мс: среда явно непригодна для подтверждения 60 FPS, причины длинных пауз/GC/GPU отдельно не изолированы. **Проверка плавности не пройдена и остаётся выпускным условием.**

QA-стенд `tests/crowd-render.html` использует реальные renderer/engine и может запускаться из локального root с сохранённым base path; он не входит в публичную сборку. Итог мобильной производительности/отсутствия мерцания на устройствах в этой работе не сертифицирован.

## Блокеры реального production

1. Подключить fixed-tick browser driver и серверный replay worker, session lifecycle, resume/reconnect, права и immutable snapshots. Текущий `game.js` всё ещё использует локальный prototype loop.
2. Реализовать адаптеры кошелька/билетов/XP/заданий/каталога/инвентаря с транзакциями, UNIQUE/idempotency, серверными лимитами и тестами конкурентности. Не переносить локальные GE/сундуки в реальные аккаунты.
3. Сделать назначение/отзыв Game Master в админке QuRa и серверные prepare/publish/audit/rollback. Клиентская проверка роли — только UI, не авторизация.
4. Утвердить слабый лутбокс, таблицы призов/дневные лимиты, правило назначения задания при отсутствии билетов и формулу общего рейтинга. Повторный XP за каждый забег отдельным тарифом не задан.
5. Пройти полный десятиминутный replay parity, тесты миграций/рестартов/повторных запросов и реальные Android/iPhone, затем gated rollout по правилам QuRa.

**Не снимать `INTEGRATED_HOST_READY=false` и `financialIntegrationReady:false`, пока эти пункты не закрыты.** Пошаговая инструкция: [PRODUCTION_HANDOFF.md](PRODUCTION_HANDOFF.md). Backend API в `integration/poultry-api.openapi.json` — проектируемый контракт, его session/receipt response schemas ещё требуют фиксации в host PR.
